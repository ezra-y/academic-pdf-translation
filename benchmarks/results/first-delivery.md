**结论：6 篇真实论文，0 篇可以直接交付。**

数据来自 `benchmarks/results/first-delivery.json`，由
`benchmarks/run_first_delivery_benchmark.py` 跑出，可重跑：

```
python3 benchmarks/run_first_delivery_benchmark.py \
    --work-dir <临时目录> --real-translation real-translation
```

论文与作业目录受版权保护，不进仓库；结果文件里只有哈希、页数和派生结论。

## 两类失败

### 一、字体覆盖缺口（4 篇）

`FONT_CHARACTER_COVERAGE_GAP`。合成译文里带着从原文抄来的数学符号
（`∈` U+2208，以及 U+F8EE 这类私用区字符），冻结字体画不出来，
候选里会退化成空字符，所以生成前就被拦下。

这是预渲染检查按设计工作。它拦的是合成译文的取材方式，不是排版缺陷。

### 二、内部返修完全无效（2 篇）

这两篇走完了整条链：生成 → 映射 → 结构对账 → 视觉检查 → 返修计划 →
重建 → 再核查 → 前后对比。结果是：

```
[!!] rebuild: 重建候选 candidate-repair-1.pdf（内容与返修前完全相同）
[!!] re-verify: 返修没有修好任何一条
```

追下去，链条的每一环都对，只有最后一环断了：

1. 返修计划正确地要求 3 个元素降级到 `preserve-element-region`；
2. `repair/forced_strategies.json` 写出来了；
3. `build_render_plan` 读到了，并且**全部生效**
   （`repair/applied_strategies.json` 里 `applied == requested`，零计划问题）；
4. **`scripts/build_candidate.py` 根本不读 `render_plan.json`。**
   全文 6405 行里 `render_plan` 出现 0 次。

也就是说：阶段 1-14 建起来的整条元素管线——元素清单、渲染计划、11 个
渲染器、三级降级链——**还没有接进生产用的候选生成器**。核查层能查出问题，
但修不了，因为它的指令到不了真正画 PDF 的那段代码。

## 这一轮修掉的三件事

1. **交付入口取错了字段名**（`candidate` 应为 `candidate_pdf`），
   导致每次都报"没有产出候选 PDF"。真跑一次就抓出来了。
2. **返修那一轮没有重算渲染计划**，降级指令连被读到的机会都没有。
3. **"返修没有修好任何一条"这句话在掩盖问题。** 它听起来像试过了没用，
   实际是一次都没试。现在交付入口比对返修前后的内容哈希（用页面文字与
   绘图、图像数量算，避开 PDF 时间戳），完全相同就直接报
   `blocked` 并写明"降级指令没有落到生成器上，这一轮返修等于没跑"。

## 未验证的部分

- **翻译性能未验证。** 本轮没有调用真实模型翻译，耗时与 Token 一概没有测量，
  也不做任何估计。表中的秒数只是核查与生成的耗时，不含翻译。
- **10 篇的目标未达到。** 仓库里有 8 篇真实论文、6 个可跑作业，
  其余论文没有配套作业；补齐需要真实模型翻译，本轮无法进行。
- **不同档位未对比。** 本轮只跑了各作业自带的档位。
